# 界面每帧成本（为什么本机 E2E 那么慢） / UI frame cost

2026-09-12 实测。起因：本机跑 Playwright 时三个内核都很慢，先怀疑显示栈（Xvfb/Weston/Docker/GPU），
最后定位到**页面自己**。

## 一、先排除环境

同一个探针（数 1.5 秒的 `requestAnimationFrame` 回调）分别量「空白页」和「本应用页」：

| 内核 | 空白页 | 应用页（启动页可见） | 应用页（音频运行中） |
| :--- | ---: | ---: | ---: |
| Chromium（headless） | **61.3 fps** | 7.5 fps | 7–9 fps（修复前） |
| Firefox（headless） | **61.3 fps** | 5.3 fps | — |
| WebKit（headless） | 58.7 fps | 0.0 fps | — |
| WebKit（Weston 有头） | 33.3 fps | 2.0 fps | — |

结论：**内核和显示栈没问题**（空白页都能到 60 fps），是应用页每帧做的事太重。
（早先记录的「Weston 1.8 fps / Xvfb 0.7 fps」也是应用页的数字，不是内核上限。）

## 二、钱花在哪

逐步隐藏元素重新测量（Chromium headless，同一台机器）：

| 状态 | 修复前 | 修复后 |
| :--- | ---: | ---: |
| 启动页可见 | 7.5 fps | **28–33 fps** |
| 隐藏启动遮罩 | 25.8 fps | 60.8 fps |
| 再隐藏所有 canvas | 58.3 fps | 60.8 fps |
| 音频运行中 | ~7–9 fps | **60.8 fps** |

三处原因，按占比排序：

1. **全屏 `backdrop-filter: blur()`**（启动遮罩、四个抽屉/遮罩、信号流详情遮罩、路由图遮罩共 7 处）：
   软件渲染下每帧都要把整个视口重新模糊一次。遮罩本身已经有 `--mask` 暗化，模糊纯装饰 → 全部去掉。
2. **画布每帧无条件重绘**：示波器、频谱（**每帧为 36 根柱子各建一个 `createLinearGradient`**）、两个迷你波形、
   滤波曲线、VU 表、以及 VU 文本与 LFO 指示灯的**每帧 DOM 写入**。改为按需：
   只在新分析帧到达时重画（`analysis.frames` 计数），或参数签名变化时重画；渐变按尺寸/配色缓存；
   DOM 只在文本/类名真的变化时写。
3. **启动页动画**：按钮的 `box-shadow` 呼吸动画（每帧重绘阴影与其模糊）与 logo 上 `filter: drop-shadow`
   包着一条动画路径（每帧重新过滤）。改成合成器友好的做法：`::after` 只做 `opacity` 呼吸、
   logo 光晕改为静态 `radial-gradient`。

## 三、回归守卫

`e2e/performance.spec.ts` 新增「音频运行中界面帧率 > 20 fps」的断言（阈值故意宽松：它要抓的是
「退回到每帧重绘」——那会让本机掉到 7 fps，而不是去考核机器性能）。

## 四、对测试与真机的意义

- 本机 Chromium 全量 E2E 从 load 8–15 下的 8.7 分钟降到约 4.2 分钟；WebKit 也整体变快（其软件光栅化仍是最慢的）。
- 手机同理：空闲界面不再每帧重绘画布、不再每帧模糊全屏，低端机更省电、更跟手。
