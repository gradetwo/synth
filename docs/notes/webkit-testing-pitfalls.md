# WebKit 自动化测试的可移植经验

> 来源：一次跨引擎回归（Chromium 全绿、WebKit 红一片）里逐条定位出来的东西。
> 这里只保留**与具体产品无关**的部分：症状、根因、做法、以及「怎么证明你的修法不是掩盖」。
> 适用对象：任何用 Playwright（或同类驱动）在 WebKit / Safari 系上跑端到端测试的项目。
> 文中出现的文件名、选择器名与数字都来自那次回归，**当例子看**——可移植的是症状与做法，不是那些名字。
> 每条都标了「症状 / 根因 / 做法 / 自证」；§0.1 是速查表，§8 是一页清单。

## 0. 先记住三句话

1. **「WebKit」不是一个目标，而是一族**：同一个 Playwright 版本，macOS 上的 WebKit 与 Linux 上的
   WebKitGTK 在输入合成、媒体特性仿真、动画时钟上都会不同。**Linux headless 全绿不能清掉 macOS 的红，反之亦然。**
2. **先分类，再修**：每一条红都要先回答「这是引擎行为、驱动行为，还是我的断言口径？」三者修法完全不同，
   而把前两者写成产品缺陷是最常见的错误。
3. **真实浏览器是便宜且决定性的裁判**：手动在真 Safari 里做一次那个动作（10 秒），经常直接判定
   「产品没问题，是测试环境」——先用它，再花小时级的时间做探针。

### 0.1 症状 → 先查什么（速查）

| 症状 | 先查 | 去哪节 |
| :-- | :-- | :-- |
| 点击/输入一次要 8–30 s，或等满超时 | 驱动的「两帧稳定」检查（无合成器时交不出帧） | §1.1 |
| 点了没反应，但事件 target 看起来是对的 | **`click` 事件是否真的派发**（捕获监听器） | §1.1b |
| 双击处理器从不运行 | 是不是 `clickCount:2` 单对 down/up、按压 0 ms | §1.2 |
| 元素位置差一个怪常数 | 动画是否推进到终态、参照系是不是 `innerWidth` | §2.2 / §2.3 |
| 某个尺寸/触控断言只有这个平台红 | **媒体查询两侧读数**；被量的是不是**原生表单控件** | §3 / §2.6 |
| 同一断言时而红时而绿 | 是否采了单帧；是否有产品去抖；先看**两个动作的间隔** | §2.5 / §6.9 |
| 某引擎上不可能通过的能力（离线重载等） | 记为**具名跳过**并打印原因，明确交给别的引擎覆盖 | §4 |
| 红了但抽不出原因 | 探针是否**先断言后打印**（失败那次就什么都没留下） | §6.10 |

## 1. 输入与手势

### 1.1 不要在 WebKit 里依赖「两帧稳定」的可操作性检查
- **症状**：一次点击 8–30 s，或直接等满超时；在无合成器的 WebKit 上尤其严重。
- **根因**：驱动的可操作性检查会等「两帧稳定」；没有合成器/软件光栅化时，页面可能长时间交不出帧。
- **做法**：给该引擎一套**帧无关**的交互实现——定时器版可见性等待、`isEnabled`、DOM 滚动、
  读包围盒、`elementFromPoint` 命中测试，然后用**真实鼠标/触摸事件**在坐标上点击。
  保留与帧无关的检查；只丢掉定义上依赖帧的那两项。**断言、阈值、超时不要动。**

### 1.1b ⚠️ 帧无关实现了之后，还要**验证事件真的被派发**
- **症状**：帧无关点击用了真实 `mouse.click(x, y)` 在正确坐标上，`pointerdown` 与 `pointerup`
  的 `target` 都对，**但引擎根本没有派发 `click` 事件**——于是看起来像「产品点了没反应」，
  而同一个动作换成驱动自己的 `locator.click()` 就正常。本次在 macOS WebKit 上复现了三次，
  失败位置在多个同类步骤间**随机**（第 2 次或第 3 次打开/关闭抽屉时）。
- **根因**：`click` 需要一对 down/up，且（在部分 WebKit 构建上）**两者要落在同一个节点上**。
  如果这中间发生了重渲染/节点替换，down 与 up 的 `target` 虽然选择器相同、节点却不同，`click` 就不派发。
  坐标相同、命中测试通过，都不足以保证 `click` 会来。
- **做法**：
  - 派发**前**在捕获阶段挂一次性监听器，记录是否收到 `click`、以及 `event.target` 是不是目标（或其后代）；
  - 没收到就**重解析坐标、重派发**，直到既定 deadline 才失败，错误信息写明「缺的是哪个事件」；
  - 给点击一个**真实按压时长**（例如 60 ms）——与 §1.2 双击同理，0 ms 按压更容易被吞；
  - 这类重试是**围绕真实手势的重试**，不是放宽断言：真到不了照样超时。**别用 retries 掩盖它。**
- **自证**：写一个探针，在页面内用捕获监听器记录每次 `pointerdown/pointerup/click/dblclick` 的 `target`，
  与「改用驱动原生点击」做 A/B。**失败那次的事件列表是唯一能定性的证据**——
  所以探针必须在断言**之前**打印，否则失败时你什么也拿不到（本次第一版探针就踩了这个坑）。

### 1.2 「双击」必须是真双击
- **症状**：`locator.dblclick()` 之后，被测元素的 `dblclick` 处理器从未运行（看起来像功能坏了）；
  同一条用例在 Chromium 绿、在 macOS WebKit 红。
- **根因**：交互封装把 `dblclick` 实现成 **`mouse.click(x, y, { clickCount: 2 })`**——只有**一对** down/up，
  且按压时长为 0。部分 WebKit 构建不会因此派发 `dblclick`。
- **做法**：发**两对 down/up**，并给一个真实的按压时长（例如 60 ms）：
  `mouse.dblclick(x, y, { delay: 60 })`（或等价的两段 `click`）。Chromium 两种都认，WebKit 只认后者。
- **自证**：写一个 A–E 变体探针（`locator.dblclick` / `+delay` / 两次 `click` / `mouse.dblclick` / `dispatchEvent`），
  在一个 spec 里打印每种之后的目标状态。谁触发、谁不触发，一目了然。
- **顺带**：单测里不要把「错误实现」钉成契约（`expect(mouse.click).toHaveBeenCalledWith(…, {clickCount: 2})`
  会把你锁死在坏实现上）；改成断言「发了真双击，且没有退回单次 click」。
- **注意**：真双击修好之后**仍可能不工作**，如果产品对双击**有意去抖**——见 §6.9。

### 1.3 区分「用户激活」与「手势合成」
- **症状**：读 `navigator.userActivation.isActive` 是 `true`，但处理器仍没跑。
- **结论**：激活存在 ≠ 事件被合成。**两者要分别测**：先确认事件到达（处理器副作用），再谈激活。

## 2. 布局与渲染

### 2.1 视口变化可能不通知页面
- **症状**：先用一个尺寸启动、再 `setViewportSize` 到目标尺寸后，依赖视口推导的布局/类别**没变**，
  于是布局断言失败。
- **根因**：某些 WebKit 构建在 `setViewportSize` 时**不派发** `resize`、`visualViewport.resize`，
  也**不触发** `ResizeObserver`。
- **做法**：
  - 测试侧：能**在目标尺寸直接启动**就不要中途 resize；否则显式设定被测状态（例如直接设置那个类别属性），
    并接受「自动识别」这一环由其它引擎覆盖。
  - 产品侧（防御）：不要让一个「可能陈旧的类别」把页面撑宽——把固定最小宽度写成 `min(设计值, 100%)` 之类，
    这样即使类别没刷新也不会溢出。这条在真浏览器里逐像素不变。
- **自证**：在 resize 前后挂 `resize` / `visualViewport.resize` / `ResizeObserver` 记录器，两引擎对比；
  再看 `data-*`/类别的实际取值。

### 2.2 CSS 动画可能永远不推进
- **症状**：几何断言失败，偏移量是个**怪但确定**的常数（本次是 7.0099 px）；新插入的同款对照元素却是对的。
- **根因**：`getAnimations()` 恒为 `running, currentTime: 0`（等几秒也不动），于是
  `getBoundingClientRect()` 量到的是**第一帧**，而不是稳定后的布局。入场动画的起止 transform 不同
  （例如 `-48%` → `-50%`），差值就是「2% 元素高度」那类常数。
- **做法**：
  - 先**把动画推到终态**再量：`el.getAnimations().forEach(a => a.finish())`，并加一个「已稳定」不变量
    （无 running 动画、尺寸回到自然大小、四边都在视口内）。
  - 或者用**布局几何**（`offsetTop/offsetLeft`）做「居中」断言，另配一条「在屏内」的渲染检查；
    但**不要**因此删掉对 transform 的检查——否则「transform 把元素放错位置」这类真回归就抓不住了。
  - `prefers-reduced-motion: reduce`（驱动大多支持模拟）能让依赖动画稳定性的一类问题直接消失，
    值得在慢引擎上默认打开。
- **自证**：`finish()` 前后各量一次（数字会跳回正确值）；再故意把终态 transform 偏移 10%，
  确认断言仍会红（证明你没把判据阉掉）。

### 2.3 参照系要用「布局视口」或元素包含块
- **症状**：偏移恰好是「滚动条宽度的一半」这类值。
- **根因**：用 `window.innerWidth` 当参照，而元素是按布局视口（`documentElement.clientWidth`）居中的；
  各引擎对滚动条（经典 vs overlay vs 隐藏）处理不同。
- **做法**：断言位置时统一用 `documentElement.clientWidth/clientHeight`，或元素自身包含块；
  **不要**用 `innerWidth`。同时区分「X 轴偏移」与「Y 轴偏移」——本次的常数其实全在 Y 轴，
  而最初的归因（X 轴、滚动条）是错的。

### 2.4 别用绝对比率量「自适应」，要量它承诺的不变量
- **症状**：填充率 0.8459 vs 阈值 0.85，差 1.1 个点，且只在某个引擎红。
- **根因**：这个比率里混进了**顶栏高度/字形度量**的引擎差异（同档另一引擎的可用高度多 8 px 就过线）。
- **做法**：断言「自适应把**受约束的那个维度**填满」（`max(widthFit, heightFit) > 阈值`）等不变量，
  而不是一个会被周边 chrome 影响的绝对比率。阈值可以原封不动。
- **自证**：把缩放改到极端（例如塌到最小值）⇒ 仍然红。

### 2.5 对「动的东西」不要只采一帧
- **症状**：亮度/像素类断言时而 94、时而 56，retry 就过。
- **根因**：被测的是一个**周期性动画**（例如脉冲），单帧采样落在脉冲的波谷。
- **做法**：在**跨越至少一个周期**的多个时刻采样并取并集/最大值，再加一条与背景的对比度下界
  （证明「不是黑盒」而不是「此刻够亮」）。阈值往往可以不动。

### 2.6 原生外观的表单控件会忽略你的盒子 CSS（macOS WebKit 实测）
- **症状**：`<select>` 只有 **19 px 高**，而规则里明明写了 `min-height:44px;padding:10px 12px`；
  同一份 CSS 在另一个平台是 48 px。同一排的 `<button>` 全部 44×44，只有 select 例外。
- **根因**：`appearance:auto`（原生外观）的 `<select>` 在 macOS WebKit 上按**原生控件度量**排版，
  **忽略 `min-height` 与 `padding`**；而 `font-size`、`min-width` **会**生效——
  所以「computed style 里有两个属性来自那条规则」并不能推出「那条规则整体生效了」。
- **做法**（二选一，取决于你愿不愿意动外观）：
  1. 让它**不要是原生控件**：`appearance:none;-webkit-appearance:none`（+ 自绘箭头）。盒子 CSS 立刻生效；
  2. **不动外观**：把控件包进一个 ≥ 目标尺寸的**容器**，让容器成为真正的手指目标
     （语义上优先用 `<label>` 包裹，激活会转发给被标注的控件；不能证明转发成立时，
     显式 `showPicker?.() ?? focus()`）。**并且断言要量那个容器**——量控件自己的盒子会永远量不到 44 px。
- **自证**：注入一个**同款新元素**到同一行，量它的盒子与 computed 样式；若新元素也一样，就是控件类型的问题，
  不是那条规则的选择器问题。再点容器**边缘**（不是控件中心），确认真的能打开/改变控件——「盒子是 44 px」
  不等于「手指够得着」。

## 3. 媒体特性与设备仿真

- **症状**：触摸目标尺寸断言在某个平台红，元素只有 19 px，而同一条在另一个平台绿。
- **第一个坑（我们踩过并被实测推翻的说法）**：一开始的归因是「触摸目标的 `min-height` 写在
  `@media (pointer: coarse)` 下，而 macOS WebKit 不把仿真设备当触摸设备、`(pointer: coarse)` 为假」。
  **实测否掉了它**：macOS WebKit 上 `matchMedia('(pointer: coarse)')` 为 **true**，而且**样式引擎也认为它为真**
  （注入一条只在 `@media (pointer: coarse)` 里生效的规则，computed 命中）。真正的原因是 §2.6（原生 select 忽略盒子 CSS）。
- **可移植的教训**：**「媒体查询读数为真」不等于「你的规则生效了」**。断言前请分别测两件事：
  1. JS 侧：`matchMedia('(pointer: coarse)').matches`；
  2. **CSS 侧**：注入一个只在那个媒体查询里才有样式的探针元素，读它的 `getComputedStyle`。
  两者不一致 ⇒ 是引擎/仿真问题；两者都为真而元素仍不对 ⇒ 去看**该元素类型**的引擎行为（如 §2.6）。
- **做法**：为「该环境下这条断言不可判定」保留一条路径：打印读数 + **具名跳过这一条**（原因上屏、
  报告里可见），同一用例的其它断言全部保留；且**只对确实不可判定的那个引擎放开**，
  其它引擎读不到就**直接失败**，这样覆盖不会悄悄消失。（但别拿它当 §2.6 的挡箭牌——
  本次那六条红**不是**不可判定，是真缺口。）
- **自证**：关掉 `hasTouch` 做对照，看读数与结果怎么变；再在能判定的引擎上故意改坏样式，确认仍红。

## 4. 引擎限制：具名跳过，不要留永久红

- **症状**：`context.setOffline(true)` + `page.reload()` 抛 `WebKit encountered an internal error`
  （Linux headless 与 macOS 都复现）。
- **做法**：这是**驱动/引擎限制**，不是产品/计时问题 ⇒ 在该引擎上**具名跳过这一条**，
  把原因**打印出来**（终端可见），并把该能力的覆盖**明确留给另一个引擎**。
- **为什么必须处理**：一条永远红的用例会训练所有人忽略红灯；「已知红」和「没人看」只差几周。
- 同类：某些引擎没有音频后端时，音频断言要**判定宿主能力后显式 skip 并打印读数**，而不是当成绿或红。

## 5. 引擎/平台矩阵

- 维护一张**能力/差异矩阵**：引擎 × 平台 × 驱动版本，记下「输入合成、媒体特性、动画时钟、滚动条、
  字体度量、离线行为」这些维度的已知差异。
- 对每条差异写明：**哪一侧是产品语义、哪一侧只是环境**，以及**本机能不能复现**。
- 「本机复现不了」要当一等公民写进记录——本次就有多条只能靠另一台机器上的读数定位。

## 6. 测试基建（与引擎无关，但正是它们把问题放大）

1. **长跑必须边跑边落盘**：把子进程输出**流式**写日志并打「开始/结束」两行。
   否则一次 2 小时的全量回归在外部看起来和卡死完全一样，只能被中止、没有任何结果。
2. **端口/配置不要硬编码进断言**：断言要走**解析后的**配置值。否则并行跑多个 worktree 时，
   测试会因为「端口被合法覆盖」而假红。
3. **区分预算与断言**：「超时」是允许一个卡住的步骤等多久；「重试」会把真抖动洗成绿。
   慢机器上应该调**预算**，并用**等被测对象自己的信号**（时钟、状态）替代猜的 sleep，而不是加 retries。
4. **让跳过可被看见**：跳过要打印原因与读数；门禁汇总里「没判」要能被看出来（但不必等同失败）。
5. **把「不可判定」与「通过」分开记账**，并在报告里给出「哪几条没判、为什么」。
6. **盲点击的命中结果是亚像素事实，不要把它写成断言**。本仓库 `e2e/roll.spec.ts` 的层条音符是
   `pointer-events:none` 的**0.75 px** 细条（在 439 px 的条里），点哪个由应用自己按 x 换算：
   同一份代码、同一组坐标，**Chromium 落到 C5@0.90 s、WebKit/Firefox 落到 G4@0.60 s**（实测，
   见 §7.4 的做法）。而两边的**编辑行为逐字相同**（一次 0.15 s、两次 nudge 后撤销回原位）——
   所以原来那条 `toContainText('0.90 秒起')` 编码的不是产品语义，是**某个内核的取整结果**。
   规则：要操作某个元素就先把它滚进视口；要证明「它动了」就断言**它自己**的变化量（相对量），
   不要断言「点中的是哪一个」。绝对字面量在命中不确定时会变成内核指纹。
7. **别在无意中测一个定时边界**。`e2e/takes.spec.ts` 的叠加用例第一遍弹了**床音自己的音高**，
   而产品有一条 50 ms 重击窗口（`TAKE_RESTRIKE`：同音高、起点差 ≤ 0.05 s 时**替换**而不是叠加）。
   录制起点 = 「点录制 → 按键」的墙钟延迟，实测 **WebKit 0.033 s**（替换 ⇒ 1 个音）、
   **Chromium 0.12–0.36 s**（叠加 ⇒ 2 个音）。**同一份产品代码，只有起点不同，计数就翻转**——
   那不是引擎差异，是测试站在了硬币边上。规则：测试要主动避开与被测语义无关的边界（换个音高、
   换一个不冲突的时隙），而不是赌它落在哪一侧；差分对照（只改起点、看计数翻转）是把这种
   「伪引擎差异」钉死的最快办法。
8. **重验证响应没有表示元数据**。`e2e/audio.spec.ts` 用响应头断言 wasm 的 `content-type`；
   Firefox 在 Service Worker 预热过 HTTP 缓存后，页面级会看到 **304**，而 304 按定义没有 body、
   也没有 `Content-Type` ⇒ 读到 `""`（页面自己的 `fetch` 拿到的仍是 `200 application/wasm`）。
   规则：表示元数据只对**完整响应**断言；重验证只能断言「它是 304」这件事本身。若某次运行全部是
   304，就用被测应用自己的信号兜底（这里是音频面板的 `流式编译`），**不要**让断言在这种情况下
   静默消失——「没判」和「通过」要分开记账（第 5 条）。
   **补充（被实测收窄）**：后来在同一台 macOS 上量到两条响应**都是 `200 application/wasm`**，
   所以「一定是 304」这个解释并不成立——**页面侧的响应读数本身无法区分**「服务器没给对 MIME」、
   「这条是重验证」、「这条是不透明的 SW 预取」。要测「服务器是否把类型给对」，就**绕过页面直接问源站**
   （请求 API 发一次同 URL），要测「浏览器是否真的流式编译了」，就断言应用自己的信号。
9. **测试可以比人快，于是撞上产品有意的去抖**。`player.spec.ts` 在 macOS WebKit 上**确定性红**：
   选中一首曲目后 ~86 ms 就双击它试图续播，而产品有一条 **450 ms 去抖**（防止「双击选曲」的第二击
   把第一击刚启动的播放按停），于是双击被**有意吞掉**。同一台机器上把间隔拉到 818 ms 就正常；
   慢机器（每次交互以秒计）永远碰不到这个窗口，所以**红只出现在快机器上**。
   规则：遇到「某引擎红、其它绿、单独跑还复现不出来/复现得出来」时，先量**两个动作之间的真实间隔**，
   与产品里的时间常数对照；若确认是测试跑得比人快，就**在测试里显式等过那个窗口并写明实测数**，
   而不是去改产品的去抖（那是产品语义），也不要用一个更长的断言超时去掩盖。
10. **探针必须在断言之前打印**。第一版探针把事件列表打在断言之后，于是失败那一次什么都没留下；
    改成「先打印、后判定」并**连续重放多次不中断**，才拿到定性的那份证据（§1.1b）。

## 7. 方法论：怎么判断「是环境还是产品」

按这个顺序，能省掉大量猜测：

1. **真实浏览器手动复现**（10 秒）：动作在真 Safari 里对不对？对 ⇒ 基本排除产品缺陷。
2. **同页对照元素**：在同一个页面里新建一个「同款但无动画/无包装」的元素，量同一个量。
   两者不一致 ⇒ 差异来自那个元素的样式/包装，而不是环境整体。
3. **逐因素消融**：一次只关一个因素（动画、touch、resize、离线），看读数怎么动。
4. **两引擎/两平台同构建对比**：同一份产物、同一个探针，换引擎或换平台各跑一次。
5. **改坏必红**：定下修法后，故意把修法破坏一处，确认断言真的会红——证明它不是掩盖。
6. **把假设写成假设**：不许拿未证实的根因去改测试、改阈值、改断言；推翻时贴原始输出。

## 8. 一页检查清单

- [ ] 手势是**真的**吗？（双击=两对 down/up + 非零按压；点击有命中测试）
- [ ] 点击之后，**`click` 事件真的派发了吗**？（捕获阶段监听器；没派发就重试而不是当成功，§1.1b）
- [ ] 失败的那次运行**留下了证据**吗？（探针先打印后断言、多样性重放，§6.10）
- [ ] 交互是否依赖「帧稳定」？在无合成器引擎上换成帧无关实现。
- [ ] 视口变化后，页面**真的被告知**了吗？（挂三个记录器验证）
- [ ] 几何断言前，动画**到终态**了吗？（`getAnimations().finish()` + 稳定性不变量）
- [ ] 参照系是布局视口/包含块，而不是 `innerWidth`？
- [ ] 量的是**不变量**（受约束维度填满）而不是会被 chrome 影响的绝对比率？
- [ ] 动的东西采样了**多个时刻**、加了对背景的对比度下界？
- [ ] 媒体特性**两侧都量了吗**：JS 的 `matchMedia` 与 CSS 引擎自己的读数（注入探针元素，§3）？
- [ ] 被量的元素是**原生外观的表单控件**吗？（它会忽略 `min-height`/`padding`，§2.6）
- [ ] 测试里的两个动作之间**比人快得多**吗？（可能撞上产品的去抖，§6.9）
- [ ] 引擎限制是**具名跳过 + 打印原因**，而不是留一条永久红？
- [ ] 长跑**边跑边落盘**了吗？端口/配置来自解析值吗？
- [ ] 每条修法都有「**改坏必红**」的证明吗？
- [ ] 记录里写清了「哪条只能在哪个平台复现」吗？
